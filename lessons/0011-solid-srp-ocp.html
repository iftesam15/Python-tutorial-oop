SOLID: Single Responsibility & Open/Closed Principles

Our BankAccount class currently balances math, manages ledger state, validates currencies, and prints console messages. Today we transition from writing working classes to designing maintainable systems using the two foundational SOLID principles: SRP and OCP.

The core idea

SOLID is an acronym for five software design principles popularized by Robert C. Martin ("Uncle Bob"). They serve as guidelines for building scalable, testable, and maintainable object-oriented architectures:

  • S — Single Responsibility Principle (SRP)
  • O — Open/Closed Principle (OCP)
  • L — Liskov Substitution Principle (LSP)
  • I — Interface Segregation Principle (ISP)
  • D — Dependency Inversion Principle (DIP)

Today we master SRP and OCP. These two principles prevent classes from turning into bloated "God Objects" and enable systems to grow without risking regressions in existing code.

1. Single Responsibility Principle (SRP)

"A class should have one, and only one, reason to change."

A common misconception is that SRP means "a class should do only one function." In reality, SRP is about actors and responsibilities. If changes to bank accounting rules (finance team) and changes to statement formatting (UI/reporting team) both force you to edit BankAccount.py, the class violates SRP.

Before vs. After SRP:

# ❌ BEFORE: Violating SRP (Managing balance + ledger + printing)
class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        print(f"[AUDIT] Deposited ${amount:.2f}")  # Presentation & logging coupled inside domain!

    def print_statement(self):
        print(f"=== Statement for {self.owner} ===")
        print(f"Current Balance: ${self.balance:.2f}")


# ✅ AFTER: Adhering to SRP (Decoupled responsibilities)
class BankAccount:
    def __init__(self, owner, balance):
        self.owner = owner
        self.balance = balance
        self.transactions = []

    def deposit(self, money):
        self.balance += money.amount
        self.transactions.append(Transaction("DEPOSIT", money))


class StatementPrinter:
    """Sole responsibility: Formatting and outputting account records."""
    @staticmethod
    def to_text(account: BankAccount) -> str:
        lines = [f"=== Statement: {account.owner} ==="]
        for tx in account.transactions:
            lines.append(f"{tx.timestamp:%Y-%m-%d %H:%M} | {tx.tx_type:10} | {tx.money}")
        lines.append(f"Final Balance: ${account.balance:.2f}")
        return "\n".join(lines)

2. Open/Closed Principle (OCP)

"Software entities (classes, modules, functions) should be open for extension, but closed for modification."

Once a class is tested and running in production, you shouldn't have to reopen its source code and add chains of if/elif/else statements every time business requirements change. Instead, design classes so new features can be added by extending (subclassing or injecting strategies), leaving original code untouched.

Interview Tip: How to explain SRP & OCP
When interviewers ask about SOLID, avoid textbook definitions like "a class does one thing." Say: "SRP states that a class should have only one reason to change, meaning it serves a single stakeholder or responsibility. OCP ensures we can introduce new system behaviors by adding new classes rather than modifying tested existing ones."
