SOLID: Liskov Substitution, Interface Segregation & Dependency Inversion

Yesterday we decoupled ledger responsibilities (SRP) and made account types extensible (OCP). Today we complete the SOLID suite with LSP, ISP, and DIP — the principles that ensure our abstractions stay honest, modular, and loosely coupled.

The core idea

The final three principles of SOLID govern how classes interact through inheritance and interfaces:

  • L — Liskov Substitution Principle (LSP): A subclass must be substitutable for its superclass without breaking client code or violating expected behavior.
  • I — Interface Segregation Principle (ISP): Clients should never be forced to depend on methods they do not use; lean, focused interfaces beat bloated "fat" interfaces.
  • D — Dependency Inversion Principle (DIP): High-level modules should depend on abstractions (interfaces/protocols), not low-level concrete implementations.

1. Liskov Substitution Principle (LSP)

"If $S$ is a subtype of $T$, then objects of type $T$ may be replaced with objects of type $S$ without altering any of the desirable properties of the program." — Barbara Liskov (1987)

In practice, if client code expects a BankAccount, passing a SavingsAccount, CheckingAccount, or VipAccount should never cause unexpected crashes, return unexpected types, or require special isinstance checks.

❌ LSP Violation: The "Locked" or "Read-Only" Account Trap

class BankAccount(ABC):
    @abstractmethod
    def withdraw(self, money: Money):
        pass

class CertificateOfDeposit(BankAccount):
    """A locked savings account with a fixed term."""
    def withdraw(self, money: Money):
        # ❌ VIOLATION: Calling code expecting BankAccount will crash unexpectedly!
        raise NotImplementedError("Cannot withdraw from a CD before maturity date!")

If a batch processing function calls account.withdraw() on a list of BankAccounts, passing a CertificateOfDeposit will blow up at runtime. A CertificateOfDeposit is not fully substitutable for a general BankAccount if it cannot honor the withdrawal contract.

LSP Golden Rules:

  • Do not weaken preconditions: Don't demand extra required parameters in subclass method overrides.
  • Do not strengthen postconditions: Don't return completely different data types or omit expected return values.
  • Preserve invariant contracts & exceptions: Only raise exceptions that caller code already expects from the base class (e.g. BankingError subclasses).

2. Interface Segregation Principle (ISP)

"Clients should not be forced to depend upon interfaces that they do not use."

Instead of creating a giant, monolithic base class with dozens of abstract methods (e.g., deposit, withdraw, add_interest, calculate_overdraft, issue_debit_card), compose smaller, role-focused interfaces.

Pythonic ISP: Role ABCs and Protocols

In Python, we achieve ISP using either lightweight ABCs or typing.Protocol (structural subtyping): 

from abc import ABC, abstractmethod

class Depositable(ABC):
    @abstractmethod
    def deposit(self, money: Money) -> None:
        pass

class Withdrawable(ABC):
    @abstractmethod
    def withdraw(self, money: Money) -> None:
        pass

class InterestBearing(ABC):
    @abstractmethod
    def add_interest(self) -> None:
        pass

# Now classes implement only what they actually support:
class SavingsAccount(Depositable, Withdrawable, InterestBearing):
    ...

class FixedTermDeposit(Depositable, InterestBearing):
    # Only deposits and earns interest — no bogus withdraw() method needed!
    ...

3. Dependency Inversion Principle (DIP)

"1. High-level modules should not depend on low-level modules. Both should depend on abstractions.
2. Abstractions should not depend on details. Details should depend on abstractions."

Consider what happens when an account sends an alert upon withdrawal. If BankAccount directly imports and instantiates a ConsoleLogger or sends an email via a concrete SMTPEmailClient, the core domain is tightly coupled to concrete I/O mechanisms.

Applying DIP with Dependency Injection:

from abc import ABC, abstractmethod

# 1. Abstraction (high-level & low-level agree on this contract)
class Notifier(ABC):
    @abstractmethod
    def notify(self, message: str) -> None:
        pass

# 2. Low-level concrete implementations
class ConsoleNotifier(Notifier):
    def notify(self, message: str) -> None:
        print(f"[CONSOLE NOTICE]: {message}")

class SMSNotifier(Notifier):
    def __init__(self, phone_number: str):
        self.phone_number = phone_number

    def notify(self, message: str) -> None:
        # e.g., integrate Twilio / SMS gateway
        print(f"[SMS to {self.phone_number}]: {message}")

# 3. High-level module depends ONLY on the Notifier abstraction
class BankAccount:
    def __init__(self, owner: str, balance: Money, notifier: Notifier = None):
        self.owner = owner
        self.balance = balance
        self.notifier = notifier or ConsoleNotifier()  # Injected dependency

    def withdraw(self, money: Money):
        # ... validation and balance reduction ...
        self.notifier.notify(f"Withdrawal of {money} completed for {self.owner}.")
