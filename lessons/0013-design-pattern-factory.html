Design Pattern: Factory & Registry-Based Object Creation

Our banking system now has four specialized account types, multiple notifiers, and distinct configuration rules. Creating these objects directly across CLI scripts or API endpoints scatters instantiation logic and violates OCP. Today we master the Factory Pattern to centralize, standardize, and dynamically extend object creation.

The core idea

The Factory Pattern is a creational design pattern that abstracts the process of object instantiation. Instead of calling concrete constructors directly (e.g. CheckingAccount(owner, balance, fee, overdraft, notifier)) throughout your application, client code requests a new instance from a dedicated factory interface.

Why direct instantiation becomes painful:

  • Scattered if/elif/else ladders: Every time a new account type is added, you must update conditional branches across every module that creates accounts.
  • Leaky configuration details: Client code (e.g. a web controller or CLI menu) shouldn't need to know internal defaults like interest rates, fee tiers, or how to wire up Notifier instances.
  • Violation of OCP & SRP: Adding new domain products forces modification of existing client workflows.

1. Simple Factory vs. Registry-Based Factory

Approach A: Simple Factory Function

class SimpleAccountFactory:
    @staticmethod
    def create_account(account_type: str, owner: str, balance: Money, **kwargs) -> BankAccount:
        acc_type = account_type.lower()
        if acc_type == "savings":
            return SavingsAccount(owner, balance, interest_rate=kwargs.get("interest_rate", 0.02))
        elif acc_type == "checking":
            return CheckingAccount(owner, balance, overdraft_value=kwargs.get("overdraft_value", 300))
        elif acc_type == "investment":
            return InvestmentAccount(owner, balance, return_rate=kwargs.get("return_rate", 0.07))
        else:
            raise ValueError(f"Unknown account type: {account_type}")

While simple factories centralize creation, the if/elif/else ladder still requires reopening the factory class whenever a new account subclass is created.

Approach B: Registry-Based Extensible Factory (Pythonic & 100% OCP)

In Python, we can leverage first-class classes and decorators to build an extensible registry factory. New account types register themselves dynamically without modifying a single line of the factory: 

from typing import Callable, Type

class AccountFactory:
    _registry: dict[str, Type[BankAccount]] = {}

    @classmethod
    def register(cls, account_type: str):
        """Decorator to register new account classes dynamically."""
        def decorator(subclass: Type[BankAccount]):
            cls._registry[account_type.lower()] = subclass
            return subclass
        return decorator

    @classmethod
    def create(cls, account_type: str, owner: str, balance: Money, **kwargs) -> BankAccount:
        key = account_type.lower()
        if key not in cls._registry:
            valid_types = ", ".join(cls._registry.keys())
            raise ValueError(f"Unknown account type '{account_type}'. Supported: {valid_types}")
        
        target_class = cls._registry[key]
        return target_class(owner, balance, **kwargs)

# Decorating classes registers them automatically!
@AccountFactory.register("savings")
class SavingsAccount(BankAccount, InterestBearing):
    ...

@AccountFactory.register("checking")
class CheckingAccount(BankAccount):
    ...

2. Factories with Dependency Injection (Wiring Notifiers)

Factories excel at assembling complex object graphs — such as instantiating the correct Notifier strategy and injecting it into the new account based on a configuration dictionary: 

class BankService:
    @staticmethod
    def create_from_payload(payload: dict) -> BankAccount:
        """
        Payload example:
        {
            "type": "savings",
            "owner": "Alice",
            "initial_amount": 1000.0,
            "currency": "USD",
            "notifier_type": "email",
            "email": "alice@example.com",
            "interest_rate": 0.03
        }
        """
        money = Money(payload["initial_amount"], payload.get("currency", "USD"))
        
        # Wire up notifier
        notifier_type = payload.get("notifier_type", "console").lower()
        if notifier_type == "email":
            notifier = EmailNotifier(payload["email"])
        elif notifier_type == "sms":
            notifier = SMSNotifier(payload["phone_number"])
        else:
            notifier = ConsoleNotifier()

        # Build account via factory
        extra_args = {k: v for k, v in payload.items() if k not in ("type", "owner", "initial_amount", "currency", "notifier_type", "email", "phone_number")}
        return AccountFactory.create(payload["type"], payload["owner"], money, notifier=notifier, **extra_args)
Interview Tip: Factory Method vs Abstract Factory
When asked in interviews:
  • Factory Method: Uses inheritance or dedicated functions to create a single product (e.g., create_account()).
  • Abstract Factory: Provides an interface for creating families of related or dependent objects without specifying concrete classes (e.g., a RetailBankFactory creating standard accounts + console notifiers vs. a CorporateBankFactory creating commercial accounts + audit loggers + webhooks).
