Design Pattern: Observer — Many Listeners, One Event

Strategy answered how this account does one job. Observer answers a different interview question: who should find out that something happened, and can they opt in or out without editing the account? Today we replace the single self.notifier with a subscription list.

The core idea

Observer (also Event-Subscriber, Listener) is a behavioral pattern: when a publisher’s state changes, it notifies every current subscriber. The set of subscribers is a list the client mutates at runtime — attach, detach, notify.

Refactoring.Guru frames the pain as a store vs its customers: either customers poll all day, or the store spams everyone. The fix is a subscription: the publisher keeps references and calls one method on each when an event fires. New subscriber classes do not require edits to the publisher — that is OCP.

The pain in our bank

BankAccount holds one self.notifier and calls self.notifier.send(...) from deposit and withdraw. SavingsAccount.deposit then hardcodes a platinum congratulations on the same notifier. Want console and email? A fraud monitor? A test spy? Today that means editing those methods or inventing a composite notifier — the publisher is coupled to a single, unknown-in-advance reaction.

Day 14 already named the notifier as Strategy-shaped DIP: how to send. That is the wrong axis for “also log this” or “stop texting me.” Observer is who listens. Keep the Notifier classes; wrap them as subscribers.

1. Publisher, subscriber, event manager

Four moving parts (cheat sheet). Because BankAccount already sits in an inheritance tree, do not force it to subclass a Subject ABC. Refactoring.Guru’s editor example patches subscription in with composition: a small EventManager the publisher holds. 

class AccountEvent:
    def __init__(self, kind: str, account, amount: float | None = None, message: str = ""):
        self.kind = kind
        self.account = account
        self.amount = amount
        self.message = message


class Observer(ABC):
    @abstractmethod
    def update(self, event: AccountEvent) -> None:
        """React to one published event. Do not return a value the account needs."""


class EventManager:
    def __init__(self):
        self._observers: dict[str, list[Observer]] = {}

    def subscribe(self, kind: str, observer: Observer) -> None:
        self._observers.setdefault(kind, []).append(observer)

    def unsubscribe(self, kind: str, observer: Observer) -> None:
        listeners = self._observers.get(kind, [])
        if observer in listeners:
            listeners.remove(observer)

    def notify(self, event: AccountEvent) -> None:
        for observer in list(self._observers.get(event.kind, [])):
            observer.update(event)


class BankAccount(ABC):
    def __init__(self, owner, balance: Money, notifier: Notifier | None = None):
        ...
        self.events = EventManager()
        sink = NotifierObserver(notifier or ConsoleNotifier())
        self.events.subscribe("deposit", sink)
        self.events.subscribe("withdraw", sink)

    def deposit(self, money: Money) -> None:
        ...  # mutate balance, append Transaction
        self.events.notify(AccountEvent(
            "deposit", self, money.amount,
            f"Deposited {money} into {self.owner}'s account. New balance: ${self.balance:.2f}",
        ))

The publisher does not know who is on the list — only that each object has update. A client (or the factory) can subscribe a second observer later. Platinum is not a print inside SavingsAccount.deposit; it is a subscriber that watches "deposit" and checks the balance.

Instance list, copy on notify

Put _observers on the instance. A class-level _observers = [] (as in some textbook samples) is one shared list — every account would notify every other account’s listeners (Day 2). And loop over list(...) so a subscriber can unsubscribe mid-notify without skipping the next listener.

2. Strategy vs Observer (say this out loud)

Both inject a collaborator. Interviews mix them up. The test is whether the caller needs a result.

StrategyObserver
How many? One (the current algorithm) Zero, one, or many
Return value? Yes — interest, fee No — fire and forget
Swap means? Different how Different who
In the bank self.interest.calculate(balance) self.events.notify(event)

Notifier.send was always a side effect. That is why wrapping it as an observer is the honest model; keeping it as the only collaborator pretended there could be only one who.

3. Python-idiomatic Observer: functions and logging

Refactoring.Guru notes that languages with first-class functions can replace the subscriber hierarchy with callables. Same rule as Strategy: no extra state → a function; config that lives across events (threshold, destination email) → a class. 

account.events.subscribe("withdraw", lambda e: print("audit:", e.amount))

You already use Observer in the stdlib. A logging.Logger is a publisher; each Handler is a subscriber. logger.addHandler / removeHandler is subscribe / unsubscribe. logger.info(...) is notify.
