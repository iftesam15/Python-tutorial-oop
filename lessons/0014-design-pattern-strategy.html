Design Pattern: Strategy — Swap the Algorithm, Keep the Account

Factory answered which class to construct. Strategy answers a different interview question: how should this object do one job, and can we change that how without a new subclass? Today we extract interest and fee math out of account types so a promo, a compounding rule, or a fee waiver is a swap — not a new inheritance branch.

The core idea

Strategy is a behavioral pattern: define a family of algorithms, put each in its own object, and make those objects interchangeable. The object that uses them is the context. It stores a strategy and delegates — it does not embed every variant in if/elif or in a forest of subclasses.

You already built this shape once without the name. Day 12 injected a Notifier and called self.notifier.send(...). That is DIP and Strategy: the algorithm for “how we notify” lives in a collaborator you can replace. Interest and fees still live inside the account classes.

The pain in our bank

SavingsAccount.add_interest multiplies by interest_rate. InvestmentAccount multiplies by return_rate. VipAccount adds a boost. CheckingAccount.withdraw always adds a flat transaction_fee. Want weekend promo rates, compound interest, or “first three withdrawals free”? Today that means another subclass or another if — the same bloating Refactoring.Guru describes for a navigator that grew a new routing method for every travel mode.

Inheritance here is doing Template Method’s job (vary a step by subclassing). That is static: the algorithm is fixed when the class is chosen. Strategy is composition: the same SavingsAccount instance can run a different interest algorithm after construction.

1. Context + strategy interface

Three moving parts (cheat sheet):

  • Strategy — one method the context understands (e.g. calculate(balance) -> float).
  • Concrete strategies — each variant of the math.
  • Context — the account: holds the strategy, delegates in add_interest / fee calculation, exposes a setter so a client can swap at runtime.
from abc import ABC, abstractmethod

class InterestStrategy(ABC):
    @abstractmethod
    def calculate(self, balance: float) -> float:
        """Return interest (or return) to deposit, given current balance."""


class FixedRateInterest(InterestStrategy):
    def __init__(self, rate: float):
        self.rate = rate

    def calculate(self, balance: float) -> float:
        return balance * self.rate


class PromotionalInterest(InterestStrategy):
    def __init__(self, rate: float, boost: float):
        self.rate = rate
        self.boost = boost

    def calculate(self, balance: float) -> float:
        return balance * self.rate + self.boost


class SavingsAccount(BankAccount, InterestBearing):
    def __init__(self, owner, balance=0, interest: InterestStrategy | None = None, notifier=None):
        super().__init__(owner, balance, notifier=notifier)
        self.interest = interest or FixedRateInterest(0.02)

    def add_interest(self):
        earned = self.interest.calculate(self.balance)
        self.deposit(Money(earned, "USD"))

    def set_interest_strategy(self, strategy: InterestStrategy) -> None:
        self.interest = strategy

The context is not responsible for choosing the algorithm — the client is. That is why a factory payload can still pick "interest": "promo" while add_interest stays a one-liner. Factory builds the graph; Strategy is the plug that graph holds.

Interview: Factory vs Strategy

Factory (Day 13): creational — “give me the right object.” Strategy: behavioral — “this object should do the same job a different way.” You often use both: the factory constructs a SavingsAccount and injects a PromotionalInterest strategy. Do not say they are the same pattern with different names.

2. Python-idiomatic Strategy: functions first

Refactoring.Guru notes that languages with first-class functions can implement strategies as functions instead of extra classes. You already did this in UserService(logger: Callable) with console_logger / file_logger.

Real Python shows a middle path: strategy classes that implement __call__, so the context can treat them like functions while they still hold state (a rate, a boost, a fee cap). 

from typing import Callable

InterestFn = Callable[[float], float]

def fixed_rate(rate: float) -> InterestFn:
    def calculate(balance: float) -> float:
        return balance * rate
    return calculate

class SavingsAccount(BankAccount, InterestBearing):
    def __init__(self, owner, balance=0, interest: InterestFn | None = None, notifier=None):
        super().__init__(owner, balance, notifier=notifier)
        self.interest = interest or fixed_rate(0.02)

    def add_interest(self):
        self.deposit(Money(self.interest(self.balance), "USD"))

Rule of thumb: no extra state → a function. Config that lives across calls (rate, boost, remaining free withdrawals) → a class or a closure. A public plugin contract you want Python to enforce at import time → an ABC, as in Day 8. Interviews often want the ABC drawing; production Python often wants the function.

3. Fees: same pattern, different family

Do not smash interest and fees into one “Policy” god-strategy. They are two families. A checking account can keep a FeeStrategy used only in withdraw: 

class FeeStrategy(ABC):
    @abstractmethod
    def fee_for(self, amount: float) -> float:
        ...

class FlatFee(FeeStrategy):
    def __init__(self, amount: float):
        self.amount = amount
    def fee_for(self, amount: float) -> float:
        return self.amount

class PercentageFee(FeeStrategy):
    def __init__(self, pct: float):
        self.pct = pct
    def fee_for(self, amount: float) -> float:
        return amount * self.pct

class NoFee(FeeStrategy):
    def fee_for(self, amount: float) -> float:
        return 0.0

Then CheckingAccount.withdraw computes fee = self.fee.fee_for(money.amount) instead of always using self.transaction_fee. Waiving fees for a month is account.set_fee_strategy(NoFee()) — OCP without a FeeFreeCheckingAccount subclass.
