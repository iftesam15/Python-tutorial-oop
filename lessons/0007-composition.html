Composition: "Has-A," Not "Is-A"

A week of inheritance has been building a family of account types. Today introduces the other half of OOP design — and starts assembling everything so far into one system: a Bank that actually has customers and accounts.

The core idea

Every subclass so far has modeled an is-a relationship: a SavingsAccount is a BankAccount. But not every real-world relationship is "is-a." A customer isn't a kind of account — a customer has accounts. That's composition: one object holds references to other objects as attributes, instead of inheriting from them.

This matters because reaching for inheritance when the real relationship is "has-a" produces nonsense: class Bank(Customer) would claim every bank is a customer, which is false and would inherit a pile of irrelevant behavior. The well-known design guideline — "favor composition over inheritance" — comes up constantly in code review and interviews for exactly this reason: it's easy to reach for a subclass out of habit when a plain attribute would model reality more honestly.

Anatomy: Customer and Bank, composed of accounts

class Customer:
    def __init__(self, name, email):
        self.name = name
        self.email = email
        self.accounts = []          # composition — a Customer HAS accounts

    def open_account(self, account):
        self.accounts.append(account)

    def total_balance(self):
        return sum(account.balance for account in self.accounts)


class Bank:
    def __init__(self, name):
        self.name = name
        self.customers = []         # composition — a Bank HAS customers

    def add_customer(self, customer):
        self.customers.append(customer)

    def total_assets(self):
        return sum(customer.total_balance() for customer in self.customers)


bank = Bank("Python National Bank")

dhrubo = Customer("Dhrubo", "dhrubo@example.com")
dhrubo.open_account(BankAccount("Dhrubo", 1000))
dhrubo.open_account(SavingsAccount("Dhrubo", 5000, interest_rate=0.03))
bank.add_customer(dhrubo)

print(dhrubo.total_balance())   # 6000.0 — Customer doesn't care which Account subclass
print(bank.total_assets())      # 6000.0 — Bank doesn't care which Customer, either

Notice total_balance never checks what kind of account it's looking at — account.balance works identically whether it's a BankAccount, SavingsAccount, or CheckingAccount, because all three share that interface from Day 4's inheritance. Composition and inheritance aren't competitors here — Customer uses composition to hold accounts, and those accounts use inheritance to share behavior with each other. Real systems use both, chosen deliberately per relationship.

The test to apply
Before writing class X(Y):, ask: "is every X really a Y?" If the honest answer is "X has a Y" or "X uses a Y," that's composition — a plain attribute, not a subclass.
