Dunder Methods: Hooking Into Python's Own Syntax

Right now, print(account) gives you an ugly <__main__.BankAccount object at 0x7f...>, and account_a == account_b is always False unless they're the literal same object in memory. Today you fix both — and it applies to every subclass for free.

The core idea

"Dunder" = double underscore. Methods like __init__ (which you already know) are Python's way of letting your class plug into built-in syntax: print(), ==, <, and more all quietly call a dunder method on your object behind the scenes. Define the right one, and ordinary Python syntax starts working correctly on your objects.

SyntaxDunder calledPurpose
print(obj), str(obj)__str__Human-readable description
repr(obj), REPL display__repr__Unambiguous, developer-facing description
a == b__eq__What counts as "equal"
a < b, sorted(list)__lt__What counts as "less than"

Anatomy: four dunder methods

class BankAccount:
    ...

    def __str__(self):
        return f"{self.owner}'s account: ${self.balance:.2f}"

    def __repr__(self):
        return f"BankAccount(owner={self.owner!r}, balance={self.balance!r})"

    def __eq__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        return self.owner == other.owner and self.balance == other.balance

    def __lt__(self, other):
        if not isinstance(other, BankAccount):
            return NotImplemented
        return self.balance < other.balance


a = BankAccount("Dhrubo", 1000)
b = BankAccount("Jack", 2000)

print(a)                          # Dhrubo's account: $1000.00 — via __str__
print([a, b])                     # uses __repr__ for each item inside a list
print(a == BankAccount("Dhrubo", 1000))   # True — via __eq__, not identity
print(sorted([a, b], key=None))   # sorted by balance — via __lt__

Because these live on BankAccount, SavingsAccount and CheckingAccount inherit all four automatically — same reuse principle as Day 4, just applied to Python's own syntax instead of your own methods.

__str__ vs. __repr__ — pick both, for different readers
__str__ is for end users: friendly, readable. __repr__ is for you, debugging: precise enough that, ideally, eval(repr(obj)) could rebuild the object. If you only define one, define __repr__ — Python falls back to it for print() too if __str__ is missing, but not the other way around.
Why NotImplemented, not just comparing blindly
isinstance(other, BankAccount) guards against comparing a BankAccount to something unrelated, like a string or an int. Returning the special value NotImplemented (not the same as raising an error, and not the same as None) tells Python "I don't know how to compare these — try the other object's method, or fall back to default behavior" instead of crashing or silently returning a wrong answer.

Today's project

Extend: BankAccount v6

These four methods go on BankAccount only — no changes needed in the subclasses, they inherit automatically.

  • __str__ — a friendly one-line description including owner and balance
  • __repr__ — a precise, code-like description (e.g. BankAccount(owner='Dhrubo', balance=1000))
  • __eq__ — two accounts are equal if owner and balance match (guard with isinstance + NotImplemented)
  • __lt__ — one account is "less than" another based on balance
  • Prove all four: print() an account, print() a list of accounts (exercises __repr__), compare two equal-looking accounts with ==, and sorted() a list of mixed account types by balance

Stretch goal: use functools.total_ordering — decorate the class with it, and with only __eq__ and __lt__ defined, you get <=, >, and >= for free. Prove one of them works.
