Polymorphism: Same Call, Different Behavior

Four days straight of nailing the stretch goal — so today folds it into the baseline. This is also where you finally resolve the overdraft tension flagged on Day 4.

The core idea

Method overriding is a subclass redefining a method it inherited, instead of just adding new ones (which is all you did on Day 4). Polymorphism is the payoff: you can call account.withdraw(amount) on a list of mixed account types — BankAccount, SavingsAccount, CheckingAccount — with zero if/elif type-checking, and each object runs its own correct version automatically. Python resolves which withdraw to run based on the object's actual class, at the moment you call it.

There are two flavors of override, and you're doing both today:

  • Replace — the subclass's version does something genuinely different from the parent's (no super() call). CheckingAccount.withdraw below is this: it can't reuse BankAccount.withdraw's "reject if amount > balance" rule, because checking accounts are explicitly allowed to go negative up to a limit.
  • Extend — the subclass calls super().method() to reuse the parent's logic, then adds something on top. SavingsAccount.deposit below is this: it still needs the real, validated deposit logic — it just adds a milestone message after.

Resolving the overdraft tension

Day 3's balance setter hard-codes "can't go below 0." A checking account with overdraft needs a different floor. The fix: make the floor itself an attribute, minimum_balance, defaulting to 0 on BankAccount — and let CheckingAccount set its own, lower one per instance. 

class BankAccount:
    minimum_balance = 0   # NEW — the floor is now a lookup, not a hard-coded 0
    ...

    @balance.setter
    def balance(self, value):
        if value < self.minimum_balance:   # reads whichever class actually owns self
            raise ValueError(f"Balance cannot go below {self.minimum_balance}")
        self._balance = value


class CheckingAccount(BankAccount):
    def __init__(self, owner, balance=0, transaction_fee=1.5, overdraft_limit=100):
        super().__init__(owner, balance)
        self.transaction_fee = transaction_fee
        self.minimum_balance = -overdraft_limit   # instance-level override

    def withdraw(self, amount):                    # REPLACE override — different rule entirely
        total = amount + self.transaction_fee
        if self.balance - total < self.minimum_balance:
            print("Amount exceeds balance and overdraft limit")
            return
        self.balance -= total


class SavingsAccount(BankAccount):
    ...
    def deposit(self, amount):                      # EXTEND override — reuses, then adds
        super().deposit(amount)
        if self.balance >= 10000:
            print("You've reached the $10,000 savings milestone!")


accounts = [BankAccount("A", 200), SavingsAccount("B", 200), CheckingAccount("C", 200)]
for acc in accounts:
    acc.withdraw(250)   # same call, three different outcomes — no type-checking anywhere
Why self.minimum_balance, not a hard-coded 0
This is the quiet trick that makes it all work: the setter lives on BankAccount and never changes, but self.minimum_balance resolves differently depending on which actual object called it. For a CheckingAccount instance, that's -overdraft_limit; for everything else, it's the class default, 0. One inherited method, polymorphic behavior, without overriding the setter itself.
