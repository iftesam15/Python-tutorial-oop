Custom Exceptions: Domain-Specific Error Hierarchies

Until now, errors in our banking system either printed a message and returned None, or raised generic ValueErrors. Today you replace silent failures with a structured hierarchy of custom exception classes that carry rich context.

The core idea

Real-world systems rarely rely solely on built-in exceptions like ValueError or TypeError. When an account withdrawal fails due to insufficient funds, the caller shouldn't have to parse a raw error message string or check if a method returned None.

By subclassing Python's built-in Exception, you create domain-specific exceptions. Organizing them into an exception hierarchy allows callers to catch specific failures (e.g., InsufficientFundsError) or catch all banking domain errors at once (BankingError).

Anatomy: an exception hierarchy with domain payloads

class BankingError(Exception):
    """Base exception for all banking domain errors."""
    pass


class InsufficientFundsError(BankingError):
    """Raised when an account does not have enough balance for a withdrawal."""
    def __init__(self, amount, balance):
        self.amount = amount
        self.balance = balance
        self.shortfall = amount - balance
        super().__init__(
            f"Cannot withdraw ${amount:.2f}: balance is ${balance:.2f} (short by ${self.shortfall:.2f})"
        )


class CurrencyMismatchError(BankingError):
    """Raised when operating on two incompatible currencies."""
    def __init__(self, currency1, currency2):
        self.currency1 = currency1
        self.currency2 = currency2
        super().__init__(f"Cannot operate between {currency1} and {currency2}")

Why exception hierarchies matter

Hierarchies give callers total control over error granularity. A caller can catch the specific error to handle it, or catch the base error as a catch-all for any domain failure: 

try:
    account.withdraw(Money(500, "USD"))
except InsufficientFundsError as e:
    # Caller can inspect structured attributes directly!
    print(f"Transaction declined: you need ${e.shortfall:.2f} more.")
except BankingError as e:
    # Catches any other banking error (e.g. CurrencyMismatchError, InvalidAmountError)
    print(f"Banking operation failed: {e}")
Always subclass Exception, never BaseException
BaseException is reserved for system-exiting events like KeyboardInterrupt (Ctrl+C) and SystemExit. Inheriting from Exception ensures your custom errors are caught by standard except Exception: clauses without accidentally blocking program termination.
Rich Payloads vs. Plain Strings
Storing attributes like self.shortfall or self.amount inside the exception object means calling code (or a UI) can make programmatic decisions (like offering an overdraft transfer or showing a tailored notification) without brittle string parsing.
